## 2. How frontier labs actually make small models strong

### 2.1 Data curation and decontamination at scale — the dominant lever

The single most consistent finding across the small-model literature is that **data quality and mixture staging beat raw parameter count**. This is not a slogan; it is the design of every strong 1B-class release below.

- **SmolLM2 (Hugging Face, 1.7B):** overtrained on ~11 trillion tokens with a multi-stage mix, not a single shuffled pile. Stage 1 (0–6T) was ~90% English web (60% FineWeb-Edu, 40% DCLM) + 10% code, no math yet. Later stages raised code to 20%, then math to 10% (InfiMM-WebMath), swapped StarCoderData for Stack-Edu, and added Jupyter notebooks. The paper's method section is explicit that dataset choice was decided by **identical-condition ablations**: 1.7B models, sequence 2048, global batch ~2M tokens, cosine schedule, LR 3.0e-4, each ablation on 350B tokens, evaluated on MMLU, HellaSwag, OpenBookQA, PIQA, WinoGrande, ARC, CommonsenseQA — and, for math/code, by *annealing* from a mid-training (3T) checkpoint rather than from scratch, because math/code capability "typically emerge only after extensive training". Sources: SmolLM2 paper, https://arxiv.org/html/2502.02737v1 ; summary of the four stages, http://www.turingpost.com/p/insidesmol
- **OLMo (Ai2, 1B):** the opposite virtue — full openness. Training data is a 2T-token sample from Dolma, documents concatenated with EOS then grouped into 2048-token instances, shuffled identically for every run so "the data order and exact composition of every training batch can be reconstructed". Hyperparameters for 1B: peak LR 4.0e-4, AdamW betas (0.9, 0.95), epsilon 1e-5, weight decay 0.1, batch ~4M tokens. Source: OLMo paper, https://arxiv.org/html/2402.00838v3
- **Decontamination is a gate, not a footnote.** The standard practice reported across sources is 13-gram overlap detection between training data and evaluation data, removing the whole document on a match, plus exact-match removal and, in newer pipelines, embedding-similarity paraphrase detection. One practitioner summary puts well-curated web corpora at under 0.5% contaminated documents — and notes, honestly, that removing them *slightly reduces* measured downstream performance, because the reduction is the removal of an inflated reading. Sources: https://ar5iv.labs.arxiv.org/html/2311.01964 ; https://www.shaip.com/blog/llm-training-data-off-the-shelf-to-production-ready/ ; https://llmbook.icsgen-ai.org/part-12-llm-systems-at-scale/module-61-scale-tools/section-61.3.html
- **XIIV translation (invent, don't copy):** XIIV already has the right raw material — FineWeb-Edu, Papers, DCLM, StackExchange, PG-19, OpenThoughts3, and a coreset/Fisher streaming design in `xiiv/coreset.py`, `xiiv/fisher.py`, `xiiv/streaming_sgbd.py` — but the *staging* discipline is missing. The frontier pattern to adopt is: (i) a fixed held-out set never used for training or mixture selection; (ii) small, identical-condition ablations to choose a mixture, not vibes; (iii) save the best math/code data for the *annealing* phase, with LR decaying to ~0 on that mixture, exactly as SmolLM2 did; (iv) 13-gram decontamination of every new training slice against the 1B harness prompt set and any benchmark set used, with the overlap report published in the run file. XIIV's own version is "SGBD annealing": freeze the 8 trained blocks, train only new parameters on a late-stage math/code/reasoning mixture, then a short low-LR consolidation — never re-training the whole model from scratch in 3 days.

### 2.2 Distillation from larger teachers — powerful, and capped

- **Llama 3.2 1B (Meta, 1.23B):** the official model card reports up to 9T tokens and, per its README as summarised in secondary sources, knowledge distillation during pretraining with logits from larger Llama 3.1 8B and 70B models as token-level targets. The tuned versions then use SFT + RLHF. Source: model card, https://github.com/meta-llama/llama-models/blob/HEAD/models/llama3_2/MODEL_CARD.md
- **Gemma 3 1B (Google, 2T tokens for 1B):** pretraining "followed a pre-training recipe similar to Gemma 2 with knowledge distillation" — 256 logits sampled per token, weighted by teacher probabilities, students learning the teacher distribution by cross-entropy, unsampled logits set to zero and renormalised. It also decontaminates the evaluation set from the pretraining mixture and applies quality reweighting. Source: Gemma 3 technical report summary, https://aisharenet.com/en/gemma-3-jishubaogao/
- **Limits, stated plainly by the literature:** a student rarely exceeds its teacher; it inherits teacher errors, biases, and outdated knowledge, often more confidently; breadth shrinks first (rare topics, long documents, unusual instructions); hard multi-step reasoning is where size matters most. The capacity-gap literature (Mirzadeh et al., AAAI 2020, via secondary summary) finds student performance *degrades* when the teacher–student gap is large, and small (≤3B) models "do not consistently benefit from long chain-of-thought reasoning" distilled from stronger reasoners — shorter reasoning examples mixed in worked better. A 2025–2026 intermediate-teacher design (BRIDGE) addresses this by inserting a mid-sized teacher assistant (~7B) between a black-box teacher and a ≤1B student, using only 3–5% of the data for the assistant, then amplifying with free assistant inference. Source: https://arxiv.org/html/2512.20403 ; summary, https://kili-technology.com/blog/model-distillation
- **Licensing warning (non-negotiable):** some providers' terms forbid using their outputs to build a competing model. XIIV must use only public, licensed, documented data and teachers whose terms allow it — the standing XIIV data rule. **Do not distill from a proprietary frontier model's outputs.** XIIV's legitimate teacher is already internal: the 133M seed / SGBD teacher activations, plus any open-weight teacher whose licence permits distillation.
- **XIIV translation:** do not chase a frontier teacher. Instead: (i) use the existing SGBD teacher-activation pipeline for the exact-1B expansion's new blocks; (ii) if a larger open teacher is used at all, use an *intermediate* (e.g. a 3–7B open model) as teacher-assistant, with short, verified reasoning traces, not long CoT; (iii) mix soft targets (teacher distribution on the shared vocabulary) with hard ground-truth labels so a teacher error cannot become a student certainty — the classic KL + cross-entropy blend.

### 2.3 Training recipes — tokens/param, schedules, annealing

- **Chinchilla (Hoffmann et al., 2022, DeepMind):** compute-optimal is roughly equal scaling of parameters and tokens, ~20 tokens per parameter (1B → ~20B tokens, ~2e21 FLOPs at that rule of thumb). Sources: https://lewislin.substack.com/p/part-8-batch-size-learning-rate-and ; https://github.com/sungeuns/foundation-model-engineering/blob/HEAD/src/pages/chapter-8/chinchilla-optimality.mdx
- **Deliberate overtraining is the small-model norm, not a mistake:** Llama 2 7B at ~2T tokens (~285× Chinchilla), Gemma 7B at 6T (~857×), Llama 3 8B at 15T (1,875×) — all cited in the overtraining literature. The reason is inference economics: pay training once, run cheaply millions of times. A 2026 paper on test-time scaling adds that overtraining is *actively beneficial* when the model will be sampled repeatedly at inference. Source: https://arxiv.org/html/2604.01411v1
- **What this means for XIIV in 3 days:** XIIV cannot and should not attempt a Chinchilla-scale retrain. The honest, frontier-consistent move is the opposite: **overtrain the small model on a narrow, high-quality, late-stage mixture** (math, code, instruction, reasoning — the SmolLM2 annealing pattern), with LR decaying to zero, on the frozen-base + new-parameters design. Token budget for 28–31 Oct should be stated in the run file as tokens actually processed, not as a target. Any "tokens/param" claim for XIIV must use the *runnable* count (773,418,240, or 857,429,760 after expansion), not the headline reconciliation.
- **Schedules seen in the wild (for calibration, not copying):** OLMo 1B peak LR 4.0e-4, cosine/linear decay, AdamW, batch ~4M tokens, warmup in the thousands of steps; SmolLM2 ablations LR 3.0e-4, batch ~2M tokens, cosine; a 1B-class SFT recipe in the wild reports LR 2e-5 (SFT) / 1.4e-3 (pretrain) with bf16 mixed precision — **UNVERIFIED as a general recipe** (single third-party model card, not a lab report). XIIV's expansion plan already uses a short LR probe before committing to a rate; keep that discipline and record the probe result.

### 2.4 Post-training — SFT, preference, and verifiable rewards (RLVR)

- **Standard frontier stack:** SFT on instruction data → preference optimisation (DPO / RLHF) → RL with verifiable rewards (RLVR) on tasks with a deterministic checker (math exact-match, code unit tests, JSON schema, countable instruction constraints). Tülu 3 (Ai2) is the fully open exemplar: ~1M instruction examples, ~1M on-policy preference pairs, then RLVR on ~10K prompts for maths and precise instruction following, a recipe reported as successfully applied to Llama 3.1, OLMo 2, and SmolLM models. Source: https://rlhfbook.com/c/03-training-overview ; RLVR definition, https://www.appen.com/blog/rlvr
- **What RLVR does and does not do (critical for XIIV):** RLVR rewards only pass/fail from a program, so it is reproducible and auditable — a natural fit for XIIV's guarantee-native thesis. But recent work warns: outcome rewards alone do *not* reliably produce causally important or verifiable reasoning (19/40 ReasoningGym tasks declined on one such metric in the cited study), and RLVR gains are often *search compression* — concentrating probability on paths the base model could already sample — rather than capability expansion. Supervised learning on a small set of high-quality reasoning traces *before* RLVR substantially improved both accuracy and verifiability in that study. Sources: https://arxiv.org/pdf/2604.22074 ; https://www.promptfoo.dev/blog/rlvr-explained/
- **XIIV translation — this is where XIIV can be genuinely original, not a port:** XIIV already has the pieces frontier RLVR lacks: a contract system (locked / required / forbidden terms compiled to sampler constraints), an independent verifier, and a proof-carrying output format. The XIIV-native post-training is therefore **verifiable-reward RL on the diffusion trajectory itself** (`xiiv/games/rl.py` design, verifiable-reward RL for chess-move legality as the first subsystem): reward = 1 only if the *final* output passes the independent verifier AND the contract constraints hold at every step — not just a final-answer match. For diffusion specifically, credit assignment must be trajectory-level (which unmasking steps committed the error), not token-level as in autoregressive RL; a 2026 survey of RL for diffusion LMs makes exactly this distinction (trajectory level × reward density). Source: https://arxiv.org/html/2610.21539
- **Scope guard for 28–31 Oct:** do not attempt a full GRPO/RLHF stack in 3 days. Do: (i) SFT-style diffusion training on instruction–response pairs where only response tokens are masked (the LLaDA SFT pattern, §2.5); (ii) a *small* RLVR pilot on 2–3 verifiable tasks (arithmetic with exact answer, short code with unit tests, constraint compliance) with the independent verifier as the reward; (iii) report pass@1 and pass@k separately, so compression is not mistaken for new capability.

### 2.5 Diffusion-specific lessons (LLaDA and successors)

- **LLaDA (Renmin / Ant, 8B, 2025):** pretraining masks tokens at a ratio t ~ U[0,1] independently per token; SFT masks only response tokens; sampling starts from fully masked (t=1) and denoises to t=0, predicting all masks simultaneously each step with flexible remasking. The 8B base was reported as surpassing LLaMA2 7B on nearly all 15 standard zero/few-shot tasks and on par with LLaMA3 8B, and as breaking the reversal curse. Sources: https://ml-gsai.github.io/LLaDA-demo/ ; https://www.alexanderthamm.com/en/blog/large-language-diffusion-models/
- **Diffusion strengths to exploit (XIIV-native):** parallel token prediction, whole-draft visibility (later passes can revise earlier words — an autoregressive model cannot), confidence-guided commit/remask, and infilling by construction. These are the *only* axes on which a 1B diffusion model can plausibly beat a 1B autoregressive model on the same hardware: revision, constraint satisfaction, and proof-carrying structure.
- **Diffusion weaknesses to engineer around:** no standard KV cache (speed must come from fewer steps, not from caching — noted in secondary coverage of LLaDA/Mercury); repetition and glitch are the characteristic failure modes when steps are too few, temperature too high, or confidence thresholds too loose; long outputs degrade because every position is re-predicted from a noisy draft. XIIV's sampler-level levers — steps, remask ratio, temperature, top_p, and the newer SetCommit (arXiv:2610.31120, training-free coordinated-token-commitment decoding for masked diffusion, from the 28 Oct research scout) and the EB-gate (entropy-bounded certificate-gated commitment, implemented 28 Oct as `xiiv/eb_gate.py`, 8/8 tests, not yet wired into generation) — are the cheapest capability levers available in 3 days, because they change *decoding*, not weights. Trial them on the GPU run with the fixed harness, one variable at a time, and keep the winner only if the harness gate moves.
- **Context 128 is a hard ceiling, not a tuning knob:** with a 128-token canvas, a prompt of 24 tokens leaves ~40 generated tokens under the harness spec (length 64) and at most ~100 tokens for a longer answer. Any "any topic" claim must be qualified by this: XIIV's 31 Oct strength is *short, structured, verified* answers, not long essays. The professional move is to state this limit in the model card and to optimise for it (concise answers, proof + reason in a few lines), not to pretend it away.

### 2.6 Inference-time scaling — the cheapest frontier trick, honestly labelled

- Frontier practice: give the model more compute at inference — more denoising steps, self-consistency (sample k, majority vote), best-of-k with a verifier, and (for reasoning) a scratchpad / self-refine pass — and report the *curve* (score vs. steps / samples / seconds), not a single cherry-picked point.
- XIIV already has the primitives: `generate_with_scratchpad`, `self_refine` (draft + remask lowest-confidence spans + re-denoise), and the guarantee lookahead. The professional discipline is: fix the *default* inference config (steps, remask, temperature) from the harness, then report a second, labelled "high-effort" config (e.g. more steps + best-of-k by verifier) as a separate row. Never report the high-effort row as the default speed or quality.
- Cost note: best-of-k multiplies GPU seconds by k. On a T4, that is the difference between a 1-second and a 10-second answer — acceptable for a benchmark, not for an interactive opencode default. The delivery package must therefore ship *two* configs: `fast` (harness default) and `verified` (high-effort), with their timings printed by the `[xiiv] … device=…` stderr line.

## 4. Professional engineering practices XIIV is missing (and how to close each by 31 Oct)

### 4.1 Reproducibility — mostly present, one gap to close
- **Present:** stitch manifest with per-tensor SHAs, whole-file SHA, config, independent audit (254 keys, runnable 773,418,240, reconciliation 915,988,480), fixed seeds in the harness, timestamped run files that are never overwritten.
- **Missing:** a single `RUNBOOK.md` that reproduces the *entire* 31 Oct pipeline from a clean checkout (data manifest → training command → stitch command → audit command → eval command → package command), with every command's expected SHA/output. Frontier teams ship this; XIIV currently ships the pieces. **Action:** write it on 29 Oct, test it by re-running the audit + harness dry-run from it, not by reading it.
- **Missing:** training-log publication. OLMo publishes W&B logs; XIIV should publish the training log (loss curves, LR, batch, tokens processed) for the exact-1B expansion and the annealing run, in the model card appendix, even if the numbers are unflattering.

### 4.2 Eval harness — built, needs two disciplines
- **Built (28 Oct):** `eval/one_b_benchmark.py` + spec + 100 prompts + competitors (all UNMEASURED) + gate (every category ≥9/10, no averaging) + SHA guard (refuses a checkpoint whose SHA does not start with `cf548ec4`) + RAM guard (refuses below 2 GB available).
- **Discipline 1 — held-out set:** the harness prompts must never enter training data. Add a 13-gram decontamination check of every new training slice against `eval/one_b_prompts.json` *before* training, and record the overlap count (0 is the target; any >0 is a failed gate, not a footnote).
- **Discipline 2 — human rating:** automated checks (`non_empty`, `contains`, `not_contains`, `max_word_repeat_ratio` 0.5) are a glitch screen, not a quality verdict. Every category score is PROVISIONAL until a human rates the same outputs. The 31 Oct delivery must therefore include a `human_ratings.csv` (prompt, model, rater, score, note) for at least the quantum prompt and one prompt per category, or the gate verdict must be labelled "automated-only".

### 4.3 Regression gates — the rule that stops silent degradation
- **Rule:** no checkpoint, sampler change, or package change ships if it regresses any of: (i) harness gate (any category below its previous score), (ii) held-out diffusion loss, (iii) identity gate for the expansion (expanded model at init must match the assembled model on same prompts/seed/steps), (iv) contract/verifier pass rate, (v) latency (tok/s on the same GPU, same spec).
- **Mechanism:** the harness runner already writes timestamped, never-overwritten run files. Add a one-page `REGRESSION_REPORT.md` per run that diffs the new run against the previous run on those five axes, with a PASS/FAIL per axis. A FAIL blocks the package, even if the headline score went up — that is how frontier teams avoid shipping a "better" model that broke something else.

### 4.4 Model card and release checklist — professional, not marketing
A frontier-grade model card (Meta, Google, Ai2 cards all follow this shape) contains, in order: model details (architecture, parameters with the counting convention stated, context, licence), intended use + out-of-scope uses, training data (sources, mixture, decontamination, licences), training procedure (hardware, steps, LR, batch, tokens processed), evaluation (harness, prompts, spec, raw run files, human ratings, caveats, *including failures*), limitations (context 128, text-only, contract excluded, repetition/glitch modes), and environmental/compute notes. **XIIV's Phase 1 card already follows this shape with measured numbers only; keep it that way.** The release checklist for 31 Oct is:
- [ ] Weights SHA matches manifest; config matches the file; tokenizer matches.
- [ ] GPU run file exists (raw output + seconds, device=cuda line).
- [ ] Harness run file exists for XIIV; competitor run files exist for at least one ungated competitor on the same hardware/spec, or the comparison is labelled "XIIV-only, competitors UNMEASURED".
- [ ] Human ratings file exists or the gate is labelled automated-only.
- [ ] Decontamination report exists (13-gram overlap vs harness prompts = 0, or gate failed).
- [ ] Failure analysis (§4.5) exists, with at least 5 dumb/glitchy outputs root-caused, not hidden.
- [ ] opencode server smoke test on a GPU machine (compile passed is not a smoke test) — or the server is labelled "compile-verified, runtime untested on GPU".
- [ ] No benchmark score, omega claim, or "beats X" claim appears anywhere without a run file behind it.

### 4.5 Failure analysis — what to do when the model gives dumb/glitchy output
Frontier teams do not hide bad outputs; they taxonomise them, because the taxonomy *is* the next training plan. For XIIV, use this taxonomy on every bad output from the GPU run and the harness, with the fix attached:

| Failure mode | What it looks like | Likely root cause (diffusion-specific) | Fix to try, in order |
|---|---|---|---|
| Heavy repetition / loop | Same word/phrase repeated, `max_word_repeat_ratio` > 0.5 | Steps too few for the length; temperature/top_p too loose; confidence commit too early (low-confidence tokens committed, then the draft collapses onto them) | More steps → lower temperature → stricter commit threshold → SetCommit / EB-gate trial (one variable at a time) |
| Incoherent word salad | Grammatical fragments, no topic continuity | Undertrained blocks for that domain; prompt tokens > canvas or prompt not frozen correctly; sampler remask ratio too high | Check prompt length vs 128 canvas; anneal on that domain; reduce remask ratio; check prompt freezing in `sample_trajectory` call |
| Prompt ignored / generic answer | Answer is fluent but does not answer the question | No SFT phase (base model, not instruct model); prompt format not seen in training; "assistant:" suffix mismatch | SFT-style diffusion training on instruction–response pairs (only response tokens masked); fix the prompt template to match training format exactly |
| Truncation / empty output | Output cuts off or is empty | Length 64 < prompt + answer; EOS predicted too early; max_tokens cap in the server (256) hit | Shorten prompt; raise length within canvas; check EOS handling in the server's `chat()` path |
| Contract / proof failure | Output violates a required/forbidden term, or the proof does not check | Contract excluded from the assembled file (by design); verifier not in the sampling loop | Do not claim contract compliance for the assembled file. For the exact-1B file, re-attach contract only after the shape defect is fixed and audited; until then, report contract pass rate as UNMEASURED / NOT APPLICABLE |
| Slow / timeout | Seconds per token far above the harness baseline | CPU fallback (check the `[xiiv] device=` line — a silent CPU fallback is a bug, not a result); too many steps; best-of-k without labelling | Verify device=cuda in the log; set the fast config as the default; report the verified config as a separate row |
| Chess / game illegality (measured 28 Oct) | No legal move generated | Model has never been trained on legal-move *format* as a verifiable task; direct prompting is not a training signal | RLVR pilot on legality (§2.4) — reward only legal moves, verified by the game engine — not more prompting |

**Rule:** every failure in the 31 Oct delivery gets a row in this table, with the raw output attached. A delivery with no failure rows is not credible for a 1B model.
